# Feed Maestro CI

`.maestro/suites/feed.json` registers these five real UI flows, in order:

1. `feed-post-crud`: create, read in list/detail, wait for loaded edit content, replace body, re-read, delete.
2. `feed-like`: like/unlike, wait for each real request to settle, re-enter detail, verify persisted counts/states, delete.
3. `feed-comment`: create parent/reply, verify the API-model parent association and visible counts/bodies, delete reply, parent, post.
4. `feed-photo`: select actual A bytes, upload, read picture identity, replace with distinct B, re-read exactly one new picture, delete.
5. `feed-form-validation`: reject empty content, open/cancel the real picker, verify no attachment, leave without saving.

Use the shared runner with `--suite feed`. `--suite ci` discovers this descriptor and includes all five flows. Directly invoking the YAML does not prepare authenticated ownership or media. This suite uses the ordinary shared lifecycle (`driver: null`), the `feed` fixture binding, and the automatically loaded `features/feed.py` preflight hook. No extra feed secrets are required.

## Prerequisites

- The genuine e2e APK, real DEV backend/OAuth/Firebase configuration, and the shared `MAESTRO_AUTH_STATE_JSON`, `MAESTRO_MEMBER_ID`, `MAESTRO_FIXTURE_START_DATE` inputs are required. Authentication refresh and registration/member verification remain in the existing bootstrap.
- Reserve the registered account exclusively for serialized CI. The four mutating flows create their own posts through the UI; they do not use an existing public post. No other actor may edit those posts or add likes/comments during the run. The feed itself is not private.
- This suite's native Android Photo Picker paths require API 33 or later. The descriptor selects API 34 for CI and raises the shared emulator minimum to 34. Use a disposable emulator with an effective ABI supported by the APK, Korean locale, Asia/Seoul timezone, and the native Android Photo Picker. A physical device is refused by photo preflight.
- API 34 `google_apis/x86_64` passed the existing root, locale, input-metadata, ABI, and APK installation guards in [CI run 38888885623](https://github.com/projects200/android/actions/runs/38888885623). The running image reported `arm64-v8a` and `x86_64`. This confirms installation compatibility for that run, not full feed-suite success.
- The gallery must contain this run's two owned PNGs exactly once. Unrelated local images may remain if their metadata cannot match either fixture. Do not connect a cloud photo account. The hook reads the complete local MediaStore without assuming query order. It rejects missing, duplicate, changed, malformed, or ambiguous metadata and never deletes unrelated media.
- Native picker rows must expose capture-date content descriptions with an `icon_thumbnail` descendant and native `button_add` confirmation. The fixture uses Android ICU skeleton `MMMdyhmmss`, sentence-initial capitalization, and the device locale/timezone. The flow taps the metadata row scoped by its real thumbnail ID. Unsupported hierarchy or missing metadata fails; no index or first-image fallback exists.

## Real media and assertions

Before any post mutation, `MaestroFeedFixture` generates two nonprivate 96×96 PNGs with Android Bitmap: A is solid red, B is solid blue. The fixture writes `DateTimeOriginal` and `OffsetTimeOriginal=+00:00` into each PNG's actual `eXIf` chunk with framework `android.media.ExifInterface.saveAttributes()`. It reopens the file and requires the parsed capture time to match before reading or hashing the final bytes. No new runtime metadata dependency or image-format migration is required.

Before generating images or reading the validation baseline, the fixture atomically records the validated member/flow/run identity with phase `pre-mutation`. After those reads succeed, the fixture atomically replaces that journal with phase `mutation-authorized`, including final filenames, SHA-256 digests, capture dates, media path, and any validation baseline. Only then can backend cleanup, MediaStore insertion, or UI mutation begin. It imports both images into `Pictures/maestro-feed/<runId>/` and publishes them with `IS_PENDING=0`. It does not assign the read-only `DATE_TAKEN`, `DATE_ADDED`, or `DATE_MODIFIED` columns. MediaProvider derives capture time from the embedded EXIF metadata during publication and later scans. A has capture time `1704153600000`, B `1704067200000` (milliseconds). The explicit UTC offset prevents scanner guesses based on file modification time or device timezone.

Preflight checks exact A/B names, ownership paths, capture times, and distinct hashes, independently of provider insertion or display order. An unrelated image with the same capture second is ambiguous and fails before selection. Android returns `FEED_IMAGE_A_CAPTURE_TEXT` and `FEED_IMAGE_B_CAPTURE_TEXT`; Python quotes those values as Java regex literals, including embedded `\\E`, and returns `FEED_IMAGE_A_SELECTOR` / `FEED_IMAGE_B_SELECTOR`. `feed-pick-image.yaml` locates the metadata row and its actual thumbnail ID, then confirms through `button_add`. The existing multipart uploader still reads the real selected URI.

Metadata support is grounded in the [framework EXIF API contract](https://developer.android.com/reference/android/media/ExifInterface#saveAttributes()) and [API 33 implementation](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android13-release/media/java/android/media/ExifInterface.java). Both support PNG `eXIf` writes. The [MediaStore capture-date contract](https://developer.android.com/reference/android/provider/MediaStore.MediaColumns#DATE_TAKEN) identifies EXIF `DateTimeOriginal` as the source. API 33 [`ModernMediaScanner.scanItemImage` and `parseOptionalDateTaken`](https://android.googlesource.com/platform/packages/providers/MediaProvider/+/refs/heads/android13-release/src/com/android/providers/media/scan/ModernMediaScanner.java) read that metadata and use an explicit `OffsetTimeOriginal` without timezone inference.

The row metadata route follows AOSP Android 13 `Item.getContentDescription`, `DateTimeUtils.getDateTimeStringForContentDesc`, and `PhotoGridHolder`. `item_photo_grid.xml` nests the thumbnail below a card and frame; `containsDescendants` avoids an invented direct-parent relationship. Korean row text places capture time before the photo type, so the regex permits surrounding localized text while quoting the exact timestamp. This source evidence does not establish installed local or CI accessibility hierarchies. Both images require runtime checks for row/thumbnail ancestry, exact formatting, unique matching, and confirmation. Keep the real upload, exactly-one-loaded-picture, and replacement-picture-ID assertions.

`E2E_RUN_ID` is the shared 16-character lowercase UUID hex identifier. The fixture returns exact ASCII `FEED_POST`, `FEED_EDITED_POST`, `FEED_COMMENT`, and `FEED_REPLY` values derived from that identifier **and** the flow name. CRUD preserves this identity while editing. The fixture knows every allowed body before UI mutation; it does not discover ownership through timestamps or loose prefixes.

Before each ASCII input, `feed-ascii-keyboard.yaml` inspects the focused Gboard layout. If its first letter key is Korean `비읍`, the flow switches language once; the same key must then expose `q` or `Q`. It does not trust the secure subtype setting alone. Each mutating flow also checks the initial post field against its exact ASCII `FEED_POST` value before submission or picker navigation. Incorrect input fails while the field is still visible, instead of being saved and then misdiagnosed as a list-refresh failure. CRUD also requires the edited field to match `FEED_EDITED_POST` before saving, so a partial replacement cannot authorize an unexpected body. The later list/detail assertions remain mandatory.

Nonempty cards expose `feed_content` only after a successful current list request and while no list request is loading. Existing cards remain visible and clickable during refresh, but cannot satisfy the list-readiness wait until that request completes. This uses the existing `hasLoadedFeeds` and `isLoading` state; it does not change refresh requests or remove post-body assertions.

The backend sorts feeds by descending ID. With stable `feedId` keys and remembered lazy-list state, Compose can retain the first visible keyed item when a new post is prepended ([`LazyListScope.items` contract](https://developer.android.com/reference/kotlin/androidx/compose/foundation/lazy/LazyListScope)). The new post can therefore be above the retained viewport, so only the initial post-submission searches use `UP`. In [Maestro run 38915419012](https://github.com/projects200/android/actions/runs/38915419012), command artifacts mark all four initial searches completed: CRUD sequence 23, like 21, comment 23, and photo 29. This supports the upward-search correction, but does not prove keyed viewport retention caused the earlier failures.

Photo detail retains `feed_detail_image_loaded`, which is present only after Coil loads the server-returned picture. Its accessibility description exposes that persisted picture ID (`feed-picture-<id>`). The flow records A's ID, waits for its absence after replacement, re-enters detail, requires exactly one persisted picture, and requires a different loaded picture ID. Old-only and old-plus-new outcomes fail. The app's edit success event alone is not accepted. The PNG digests prove the prepared inputs differ; the flow does **not** require returned server/CDN bytes to retain those digests or invent an image-transformation contract.

Reply text carries a model-backed `feed_detail_reply_to_<parent content>` tag from the API's nested `children` mapping. The flow requires the intended unique parent body, reply body, association tag, visible ordering, and count two. A second root comment cannot satisfy that association. After sending the parent, the flow dismisses the keyboard. A required `scrollUntilVisible` then seeks the unique `답글` control downward with a 20000 ms timeout and `centerElement: true`. The tap and reply-banner assertion remain mandatory. The flow dismisses the keyboard again after sending the reply, before association/count assertions and deletion. Like waits observe the real debounced request's pending state; both original detail re-entry persistence checks remain.

## Failure cleanup and limits

The shared finally path invokes `MaestroFeedFixture.cleanup` through the same authenticated session, before ordinary session teardown. Successful UI post/comment deletion remains part of each consumer test; backend cleanup is a failure safety net, not a replacement for UI assertions.

Prepare rejects any existing journal, including one for the same owner, with `feed_fixture_snapshot_exists`. It preserves ownership-mismatch and corrupt-journal failures instead of replacing recovery evidence. If baseline retrieval fails, prepare still reports that failure. Only cleanup for an intact, matching-owner `pre-mutation` journal can return without any backend or media calls. Cleanup retains that journal so later shared-cleanup failures can retry. This feature-cleanup result does not convert failed prepare into a passing flow. Missing or corrupt journals, unknown phases, and ownership mismatches remain failures; the feature never clears common recovery markers itself.

- Cleanup traverses **all** feed pages and collects candidates before deletion. Both verified member ownership and an exact current-run/current-flow original or edited body must match. It re-reads each candidate before mutation; renamed or re-owned posts are preserved.
- Cleanup validates every candidate's comments before any delete. It re-reads comments immediately before deleting them. Only the exact run-owned parent/reply bodies from the same member are eligible. Foreign or unexpected comments fail cleanup and preserve the post; cleanup does not use post deletion to bypass that failure. The dedicated-account/no-concurrent-writer prerequisite remains necessary because these APIs provide no atomic compare-and-delete transaction.
- For remaining owned posts, cleanup explicitly deletes eligible replies, then parents, checks the comment list is empty, deletes exact picture IDs, rechecks ownership and an empty picture list, then deletes the post. A final full feed traversal must find no owned post. Every repository/read/delete error fails cleanup with a fixed nonsecret error. It does not infer success from an unspecified missing-resource status.
- In phase `mutation-authorized`, form validation requires the same authenticated member's complete ID set captured before mutation. A missing baseline or an unexpected unmarked/empty post fails with `feed_validation_unexpected_posts`; neither condition qualifies for the `pre-mutation` cleanup path. Cleanup preserves that post rather than guessing ownership and deleting an unrelated account post. The private baseline remains available for operator investigation.
- Media cleanup deletes only rows with this run's exact path and A/B filenames, including partial imports, then queries for their absence. It does not clear the gallery. Feature cleanup **retains** the private journal and validation baseline, including after a successful feature cleanup. If later exercise cleanup or session removal fails, the same member/flow/run request can repeat feature cleanup against the original baseline. Ownership mismatches and changed baselines still fail without deleting evidence. The host removes app-private evidence only through the final successful `pm clear`, after feature cleanup, exercise cleanup, and session removal succeed. The common runner preserves recovery state and stops subsequent flows when cleanup fails.
- Successful UI post deletion exposes no remaining post detail for explicit child cleanup. Android client source does not establish backend cascade, hard deletion of already deleted-post attachments, object-store removal, or CDN retention. This suite proves UI/API post absence, not those storage guarantees.
- A process/device/CI termination before finally may leave the exact run's backend post or media. There is **no** historical-prefix sweep. Preserve the private journal and the same member/flow/run identity for recovery through the shared authenticated cleanup operation. Clearing app data or discarding that journal before failed cleanup loses automatic recovery metadata; operator recovery must identify exact owned IDs and must not delete other account posts. Legacy `e2e612-*` posts and other runs are deliberately untouched.
